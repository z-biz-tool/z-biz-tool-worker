## 8.2 改了什么

### 8.2.1 并发认领竞态（B3 / W-07～W-12）—— 真缺陷，已修

**原状**（`commands.rs::assign_task`）：

```
find_task(id)  →  改内存里的 task  →  save_task(&task)
```

`save_task` 是**无条件 upsert**（`ON CONFLICT(id) DO UPDATE SET …` **不带 WHERE**），
而 `find` 与 `save` 各自持锁、中间有窗口 ⇒ **两个 Agent 同时领同一个任务时，后写的覆盖先写的**：
先写的那个 Agent 已经在跑 LLM（`run_task_background` 已经 spawn 出线程），
但任务归属被改掉了 —— 谁也不知道任务到底归谁。

**现在**：三条写路径全部改成**带 WHERE 的单条 UPDATE**（`src-tauri/src/db.rs`）：

| 函数 | WHERE 条件 | 语义 |
|---|---|---|
| `claim_task` | `id = ?1 AND status = ?5 AND assigned_agent_id IS NULL` | **抢**一个还没人领的任务：只允许一个赢家 |
| `reassign_task` | `id = ?1 AND assigned_agent_id = ?2` | **用户显式改派**：中途被别人改派过就失败，不顶掉对方 |
| `release_task_agent` | `id = ?1 AND assigned_agent_id = ?5` | **释放**：中途被改派时不误清别人的绑定 |

条件不成立 ⇒ `affected_rows == 0` ⇒ **明确报错**，不静默覆盖。

**为什么分成"认领"与"改派"两条路**：
两者面对的是**不同语义**。抢单是并发（只允许一个赢家），
改派是**人的意图**（任务详情面板的「分配给」下拉框），后者后写覆盖先写是应有之义。
但**改派也带条件**（`assigned_agent_id = 旧值`），以免读-写窗口里顶掉别人。

**顺带修掉两处状态不一致**：

1. **任务挂着已释放的 Agent**：`update_task_status("done")` 与 `review_task` 原来只把
   Agent 置回 `idle`，**没清** `task.assigned_agent_id` ⇒ 任务已完成，
   界面却还显示"已分配给某某"，而那个 Agent 已经空闲。
   现在释放绑定走**条件 UPDATE**。
   ⚠️ **落盘顺序不能反**：`save_task` 是**整行 upsert**，写的是内存里那份 task
   （此时 `assigned_agent_id` 还指着旧 Agent）—— 先释放再 `save_task`，
   那次 upsert 会把刚清掉的绑定**原样写回去**。所以代码里是**先 `save_task`、后 `release_task_agent`**。
2. **改派后旧 Agent 永远卡在 `working`**：原实现改派只改任务上的绑定，
   旧 Agent 的 `status` 仍停在 `working`、`current_task_id` 仍指着已经不属于它的任务。
   现在改派时把旧 Agent 放回空闲 —— 但**只在旧 Agent 确实在跑这个任务时**
   （`current_task_id` 对得上）才动它，免得误伤正在干别的活的 Agent。

**顺带一个耦合点**（不写下来将来一定会踩）：
`review_task` **不通过**时任务回到 `todo`，此时**必须**清掉绑定 ——
因为 `claim_task` 的条件是 `assigned_agent_id IS NULL`，
留着绑定的话任务回到 `todo` 却**谁都领不走**，是个死局。
已用闭环用例 `released_task_can_be_claimed_again` 钉住。

### 8.2.2 状态流转规则抽成纯逻辑模块（B2 / W-05 / W-06 / W-13）

**原状**：流转规则散在 `commands.rs` 的三处 `if` 里（合法状态白名单、盖 `completed_at`、
释放 Agent），而这三条命令都依赖全局 DB（`storage::get_db()`）⇒ **没法在单测里驱动**
⇒ 这些规则**一行测试都没有**。

**现在**：新增 `src-tauri/src/task_state.rs`（174 行，纯逻辑、不碰 IO）：

- `VALID_STATUSES` / `is_valid_status` / `validate_status` —— 5 个合法状态 + 未知状态被拒
- `plan_status_update(status)` —— 要不要盖完成时间、要不要释放 Agent
- `plan_review(approved)` —— 落到哪个状态、要不要盖时间、要不要释放 Agent

`commands.rs` 改调同一份规则，**行为不变**，只是「规则」与「副作用」分了家。

**顺带得到一个明确的现状结论**：`done → doing` 这类回退**当前是被接受的**
（`update_task_status` 只校验状态**取值**合法，不校验**从哪来**）。
看板拖拽是本仓的核心交互 ⇒ 本轮**不新增状态机**，只把现状钉进测试（`only_done_releases_agent` 等）。

### 8.2.4 时区/夏令时漂移：量清楚，不改行为（W-16）

`start_date` / `due_date` 存的是 `YYYY-MM-DD`（无时刻），
`new Date("2026-01-01")` 按 ES 规范解析成 **UTC 午夜**；
而时间轴用**本地时区**的 `setDate` 做日期加减。
两套坐标系混用 ⇒ **值得量一量到底会偏多少**。

- **量法**：探针脚本，**8 个时区 × 6 个日期 × 4 个时刻 = 192 组**，
  逐组比较 `ganttBarStyle` 的 `left` / `width`。
- **结论（两条）**：
  1. **任务条定位**：192 组里 **10 组**在美东/美西时区偏**一格**，
     且都出现在跨夏令时切换点附近。**UTC+8（Asia/Shanghai）恒定** ⇒ 中国大陆用户不受影响。
  2. **时间轴长度**：`totalDays` 用「毫秒差 / 一天」向上取整，
     而 `setDate` 走本地日历 ⇒ **冬令时回拨**（11 月）那次多 1 小时 ⇒
     `totalDays = viewDays + 1`（实测：美东 121 / 柏林 121 / UTC 120 / 上海 120 / 东京 120）。
- **处理**：**只量清楚，不改行为**。改成"按日历天算"会挪动任务条位置，
  属于**用户可见的产品变化** ⇒ 交给决策人，本轮不擅自做。

> ⚠️ **记一条我自己被推翻的判断**（留在这里是因为它是现场）：
> 抽离模块时我先在注释里写了「负时区任务条整体偏一天」，
> 写完**立刻去实测** —— 探针打回来**不成立**：8 个时区里定位几乎全部一致，
> 只有夏令时切换点附近那 10 组才差。
> ⇒ 注释已按实测改正。
> **教训**：「日期字符串按 UTC 解析」与「本地 `setDate`」混用会**看起来**像必然偏一天，
> 但 `ceil` 与锚点的时刻成分会把它抵消掉 —— **不实测就是在编**。

### 8.2.5 统计口径的两份实现（C5 / W-19）

`get_project_stats` 在**两个地方各写了一遍**：
`db.rs`（SQL 侧只取 `status` 列）与 `commands.rs`
（把该项目的任务/Agent **全读出来**再在 Rust 侧 filter）。

**同一套统计规则写了两遍，两遍实现方式还不一样** ——
字段一改只有一边跟着改，数字对不上时没人知道该信哪个。
这正是「同一套规则在两侧各写一遍必然漂移」的形态。

**处理**：`commands.rs` 改调 `storage::get_project_stats`（收敛成**一份**），
并补 4 条单测锁住口径（含 **project 过滤** —— 漏了这条，项目面板会把别的项目的任务算进来）。

### 8.2.6 三个从未被构造的结构体（C6 / W-20）

`models.rs` 里的 `TaskDependency` / `TaskAttachment` / `WorkflowTemplate`
**零构造、零引用**（`grep` 全仓只命中各自的 `pub struct` 定义处）。

这三张表在 `init_schema` 里建了，读写走**裸 SQL**；
而 Rust 侧又各放了一个"类型化镜像" ⇒ **同一份结构写了两遍**（一遍 DDL、一遍 struct）。
字段一改就漂移，而**编译器不会报**（因为镜像根本没被用过）。

**处理**：删掉三个结构体，在原位置留注释：
「将来要做类型化接口，请**结构体 + 类型化访问器一起加**，不要只加结构体」。

## 8.4 变异反向验证：判据咬得住

否则上一条的失败会泄漏到下一条），还原后**核对文件哈希**。

**脚本**：`/tmp/worker_mutation.py`（独立 python 文件，备份走内存字节快照，

## 8.7 2026-10 补做：W-01 / W-02 / W-03 / W-17 与 900×600 适配

> 对应 [05](./05_实施路线与任务拆解.md) 中 W-01～W-03、W-17 以及 2026-10-26 交互契约轮。

### W-01 孤儿进程回收
- `agent_proxy.rs`：子进程独立进程组；父进程被 SIGKILL 后由 ppid 看门狗在数秒内退出，
  连带杀掉 CLI 进程组；删除 Agent 时调用代理 `POST /v1/session/close`。
- 测试：`kill_takes_down_the_whole_process_group`、`parent_sigkill_takes_down_proxy_via_ppid_watchdog`、
  `kill_leaves_processes_outside_the_group_alone` 等（真实起进程，非 mock）。

### W-02 node 解析不再依赖 `which`
- 改为显式扫 PATH（空/缺失跳过）→ 常见安装目录 → nvm → 裸 `node`；
  PATH 为空、PATH 无 node 两类分支各有单测。

### W-03 stdout/stderr 有上限且不阻塞
- stdout/stderr 各 2048KB 上限，超限后**继续 drain** 而不是停止读取（避免子进程写满管道卡死）；
  覆盖 2MB 输出、单条巨行、真实子进程 1.5MB 三种用例。

### W-17 四视图纯逻辑抽出
- `src/utils/{kanbanLayout,listView,dashboardLayout,documentsLayout}.ts` + 对应测试；
  覆盖分组/目标解析、批量结果汇总、`completedRate` 不伪造 0%、删除后选中项不越界。

### 900×600 窗口适配（本轮实测修复）
- `App.tsx`：内层 `Layout` 补 `minWidth: 0`，避免看板内容把**整页**撑出横向滚动条。
- `TopBar.tsx`：标题与导航允许换行；项目名 120px 省略；搜索框 `flex:0 1 150px`。
  回归过一版「导航横向滚动 + 居中」导致当前 tab 不可见的错误做法，已改回 `flexWrap` 方案。
- 证据：Chrome headless CDP，900×600，8 个视图逐一截图；每页 `scrollWidth == 900`，
  7 个导航 tab 同一行可见（y=28），搜索框落到第二行；快捷键、任务抽屉、Agent 删除确认、
  搜索过滤、设置返回均走通，0 未捕获异常。
