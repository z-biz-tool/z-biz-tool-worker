## 9.1 一句话

本轮把 **「同一个 Agent 有好几套说法」** 这条主线一次收干净：

- 后端有**三套**互不相认的「这个 Agent 是什么」—— 库里的 `agents.cli_type`、
  会话覆盖表 `agent-sessions.json` 的 `cli_types`、以及硬编码的代理地址；
- 执行有**两条**互不相干的路径 —— 对话走**有状态**会话、任务自动执行走**无状态**路径
  （每次新开一个 CLI 会话、不带任何历史）；
- 而**界面上那个「对话」区从头到尾没有渲染过** ——
  `messages` 被加载、被追加，却从不上屏。

⇒ 结果是：用户在一个任务面板里发消息、**一个字都看不见**；
任务自动跑完的结果**不进入对话历史** ⇒ Agent **看不见自己刚交付的东西**；
卡片上写着「Hermes」的 Agent，**对话里跑的却是 Claude Code**。

## 9.2 改了什么

### 9.2.1 P0 · 交互：对话区**从来没有渲染过**（`TaskDetailPanel.tsx`）

**原状**（实测：`grep -n "messages" src/components/TaskDetailPanel.tsx`）：

```
52:  const [messages, setMessages] = useState<TaskMessage[]>([]);
63:      const msgs = await invoke<TaskMessage[]>("get_task_messages", { taskId: task.id });
157:      setMessages([...messages, result.user, ...(result.agent ? [result.agent] : [])]);
```

⇒ `messages` 只有**写**、没有**读进 JSX**；全仓 `grep -rn "TaskMessage" src/`
只有这一处引用 ⇒ **界面上从来没有对话区**。
用户点「发送」⇒ 后端把消息**存进 SQLite** 了、`get_task_messages` 也读得到，
**但界面一个字都不显示** ⇒ 用户以为「消息没发出去」，
而库里明明有 ⇒ 而且重开面板还是空的（因为压根没渲染）。

**修法**：
① 把对话渲染出来（谁说的 / 什么时候 / 内容）；空态给两句话
（有 Agent ⇒「可以直接给 Agent 发消息」；没 Agent ⇒「消息会被记下来，但没人回复」）；
② 后端在「没有分配 Agent」时返回 `agent: null`（消息已落库、没人回）⇒
   前端**明确提示**「消息已记录，但这个任务还没有分配 Agent，暂时没人回复」
   （原来只弹「发送失败」，用户分不清是没发出去还是没人回）；
③ 任务被更新（后台自动执行跑完了 ⇒ `task.updated_at` 变了）⇒ **刷新对话**
   （原来 5 秒轮询只更新 `task`，不更新本面板的 `messages`
   ⇒ 自动执行的结果要等**关掉再打开**面板才看得见）。

### 9.2.2 P0 · 功能：自动执行的结果**不进对话历史** ⇒ Agent 失忆

**原状**（`commands.rs::run_task_background`）：成功时只写
`t.output` / `t.agent_output`（任务上的两个字段），**不写 `task_messages`**。
而 `send_task_message` 组上下文时**只读 `task_messages`** ⇒

> 任务卡片上明明显示着 Agent 的产出，用户在下面的对话框里问
> 「你刚才那个结果里 X 是多少」，Agent **答不上来** ——
> 因为它看不见自己刚交付的东西。

**修法**：后台执行成功/失败都写一条 `role="agent"` 的消息
⇒ 用户在对话区看得见，Agent 的上下文里也有。
面板上的「Agent 输出」块**在同样内容已经出现在对话里时不重复显示**
（同一份内容不显示两遍；旧数据的产出没有进对话 ⇒ 仍然显示）。

### 9.2.3 P0 · 功能：对话路由的 CLI 与卡片上写的 CLI **可能不是同一个**

**原状**：两个「CLI 类型」各说各话：

| 说法 | 存在哪 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| `agents.cli_type` | SQLite `agents` 表 | `import_local_agent` | **自动执行**（`run_task_background`） |
| `agent-sessions.json` 的 `cli_types` | `~/.local/share/future-team/` | `set_agent_cli_type` | **对话**（`run_agent_turn_inner` → `cli_type_for`） |

⚠ 而 `set_agent_cli_type` **前端从来没调过** ⇒ 那张覆盖表**永远是空的**
⇒ `cli_type_for` 永远返回兜底值 **`claude-code`**
⇒ **卡片上写着「Hermes」的 Agent，对话里跑的却是 Claude Code。**

**修法**：`resolve_cli_type` 把三层收成**一条真源**（纯函数，有单测）：

```
用户显式覆盖（set_agent_cli_type） > Agent 自己声明的（agents.cli_type） > claude-code
```

对话与自动执行**都**用它 ⇒ 同一个 Agent 在两条路上是**同一个东西**。

### 9.2.4 P0 · 功能：自动执行与对话**不是同一个会话** ⇒ 重试从零开始

**原状**：`run_task_background` 走 `agent_runner::run_agent`
⇒ 每次 `/v1/session/open` **开一个新会话**、**不带任何历史**
⇒ ① 自动执行与面板对话是**两个互不相干的对话**；
② **重试**每次都从空白开始（Agent 忘了上次跑到哪、也忘了用户的追问）。

**修法**：
① 删掉 `agent_runner.rs`（**无状态路径整体退役**），
两条路统一走 `agent_session::run_agent_turn_inner`（**同一个 Agent ⇒ 同一个 proxy session**）；
② 后台执行把这条任务**已有的消息**当上下文带进去 ⇒ 重试能接上；
③ `assign_task` / `retry_task` 改成 `async` 命令 + Tauri 异步运行时（原来是 `std::thread`）。

### 9.2.5 功能 · 代理地址与代理路由：**两处真源分裂**

| 症状 | 原状 | 修法 |
| --- | --- | --- |
| 同一个代理有两套地址 | `chat()` **硬编码** `http://127.0.0.1:9099`，而设置项 `agent_proxy_url` 只有 `discover_local_agents` 在读 ⇒ 用户改了地址，**发现面板连新的、对话连老的** | 两边都走 `agent_session::proxy_url()`（配置优先） |
| 同类型的 Agent 会路由错 | 只发 `X-CLI-Type` ⇒ 代理按**类型**取第一个 Agent 的配置 ⇒ 同类型有多个时用错那一个 | 补发 `X-Agent-Id`（用 `agents.local_agent_id` —— 这个字段**存了但从来没用过**）⇒ 精确路由到**那个** Agent |

### 9.2.6 能力 · 「Agent 会话」管理面接进 UI（家族探针点名的 6 个孤儿之一组）

`get_agent_session` / `set_agent_cli_type` 两个命令**前端从来没调过**
（家族探针 `family_probe_orphan_commands.py` 实测：worker 38 个注册命令里
它们属「连提都没提」那一档）⇒ 用户没法决定某个 Agent 用哪个 CLI 对话。

**修法**：Agent 卡片的下拉菜单加「切换 CLI 类型」
⇒ 先 `get_agent_session` 读当前**生效中**的值（并显示会话 id，便于排障），
再 `set_agent_cli_type` 写覆盖值（**对自动执行与对话同时生效**）。
手填 Agent（`source != "local"`）这一项**置灰** —— 它没有 CLI 类型可言。

### 9.2.7 工程 · CI 会被一条 lint 弄红（**推上去就红**）

`abe57ce` 引入的 `taskkill_tree_args` **只在 `#[cfg(windows)]` 分支被调用**
⇒ 非 Windows 的**非测试**构建里它是死代码 ⇒ CI 的
`cargo clippy --all-targets -- -D warnings` **rc=101**（实测）。

⇒ 用 `#[cfg_attr(not(windows), allow(dead_code))]` **精确豁免这一条**
（不是整仓关掉这个 lint）：真要治它，就得把这段参数构造在两个平台各写一遍
⇒ 反而更容易漂移。测试（`taskkill_tree_args_shape`）在所有平台都跑
⇒ 逻辑本身一直有覆盖。

### 9.2.8 家族能力 · IPC 契约门进仓（家族第 4 个带上这道门的仓）

`tests/ipcContract.test.ts`（**9 例**）守两件事：
① 前端调的命令**后端必须真的注册**（点了必崩 = 0）；
② 后端注册的命令**要么被前端调用，要么登记为「预留未接线」并写明理由**。

与 note / box 的版本不同的地方（**本仓形态决定的**）：
- **Rust 侧必须先剥注释** —— 本仓 `generate_handler!` 体内有注释掉的条目
  （`// commands::delete_file 已移除`）⇒ 不剥注释就会把**注释里的命令**当成已注册
  ⇒ 家族探针因此报出过「后端注册了一个叫 `commands` 的命令」这种胡说；
- **handler 体按逗号切、一段必须完整匹配一条路径才算数**
  （`commands::list_projects` ⇒ `list_projects`，**不是** `commands`）；
- 前端侧认**嵌套泛型**（`invoke<Record<string, unknown>>("x")`）。

**变异验证 9 组全杀**（每组都把源文件改坏再跑，最后无论成败都还原）：

| 变异 | 门禁 |
| --- | --- |
| 前端调了后端没注册的命令 | ✅ 红 |
| 后端注册了没人调的命令 | ✅ 红 |
| 预留清单里写了**已经接上**的命令 | ✅ 红 |
| 预留清单里写了后端**没注册**的命令 | ✅ 红 |
| Rust 侧不剥注释 | ✅ 红（自证先红） |
| JS 侧不剥注释 | ✅ 红（自证先红） |
| 嵌套泛型不认 | ✅ 红 |
| 正则字面量不认 | ✅ 红 |
| handler 路径前缀取错段 | ✅ 红 |

⚠ **本轮又踩了一次等价变异**：正则那条的自证样本最初写成
「正则 + 一条真命令」⇒ 剥注释器把字符串**原样保留** ⇒ 文本没变 ⇒ **读数没变**
⇒ 那组变异**根本没测到东西** ⇒ 改成「正则里的引号把**后面那行注释**吞进字符串」
（不认正则 ⇒ 注释被当字符串内容保留 ⇒ **多读**出一个注释里的假调用点）后重咬。

## 9.4 本轮**没做**的（明确记账）

| 事项 | 为什么没做 |
| --- | --- |
| `get_agent_status` 接线 | 与 `list_agents` 返回的 `agent.status` **重复**；要单独接它，得先有「Agent 实时状态」面板（UI 未定）⇒ 登记为「预留未接线」 |
| `batch_update_tasks` 接线 | 看板多选批量改状态是**独立需求**，交互（多选框放哪、能不能跨列）要先定 ⇒ 登记为「预留未接线」 |
| `list_agent_sessions` 接线 | 会话总览是诊断视图；等有「Agent 会话面板」这个需求时，和它一起做 ⇒ 登记为「预留未接线」 |
| `agent-sessions.json` 的权限与内容（W-24） | **2026-10-27 已量到并落地**（05 §5.5、08 §8.7）：文件 0600、目录 0700；内容只有 `sessions`（agent_id → session_id）与 `cli_types`（agent_id → 类型），不含提示词/密钥/对话；证据 `agent_session::tests::session_file_is_private_and_contains_no_prompts_or_secrets`，本轮 `cargo test --lib` 56/56 复跑通过。加密仍不做，属产品取舍 |
| 孤儿进程回收在「应用异常退出」时的端到端验证（W-01） | 进程组 + ppid 看门狗已由**真实进程**用例覆盖（`parent_sigkill_takes_down_proxy_via_ppid_watchdog`、`kill_takes_down_the_whole_process_group` 等，本轮 56/56 复跑通过）；但**打包后的 GUI 应用被系统杀掉**这条端到端取证仍未做，不写成「全场景已验」 |

⇒ 「预留未接线」清单**在契约门里**，且门禁守着
「接上了就必须从清单里删掉」「清单里的命令后端必须真的注册着」
「每条都要写清理由」三条 ⇒ 它不会变成「忘了接线」的遮羞布。

## 9.5 对产品行为的影响（诚实交代）

用户可见的变化有 **5 处**，都是**修不一致**、不是**加限制**：

1. **对话区现在真的有内容了**（原来一个字都不显示）。
2. **任务自动执行的结果进对话区了**（原来只在任务字段里，Agent 看不见）。
3. **对话与自动执行走同一个 CLI**（原来对话永远走 claude-code）。
4. **重试会带上历史**（原来每次从零开始）。
5. **Agent 卡片可以切换 CLI 类型**（原来只能改 Agent 自身的 `cli_type`，且没有入口）。

**没有**做的事：没有加状态机、没有限制拖拽、没有改任何默认参数、
没有动 `agent-proxy` 与前端依赖版本、没有删任何**用户可见**的命令
（删掉的 `run_agent_turn` **前端从来没调过**，它是「绕过消息持久化」的后门入口）。

## 9.6 2026-10-30 收尾：更新器释放资源的空 catch 留痕

`src/components/UpdaterDialog.tsx` 的 `dismiss()` 在未安装更新时会主动 `update.close()` 释放 Rust 侧资源，
原来是 `.catch(() => {})`。释放失败不影响用户可见行为，但会藏掉「资源没释放」这一事实。
现改为 `console.warn("[updater] 释放更新资源失败:", e)`，与同文件检查更新失败的日志口径一致。
